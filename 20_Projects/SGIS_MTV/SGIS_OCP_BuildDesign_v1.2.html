01. 개요

이 문서는 국가데이터처 SGIS 오픈플랫폼의 VMware 환경을 OpenShift로 전환하기 위한 구축 설계 기준입니다. 구축팀이 설치·구성에 사용할 장비 배정, 사양, 네트워크·스토리지 설계 값, 설치 파라미터와 MTV 이관 설계를 정리합니다. 일정·회차·검증 절차 등 고객 설명용 내용은 별도 작업계획서에서 관리하며, 설계 값이 서로 다르면 이 문서를 기준으로 작업계획서를 고칩니다.

OpenShift 클러스터2개외부망 1 / 내부망 1 · 망별 독립
망별 노드3 + 2Master VM 3식(KVM 1대) · Worker 2대
이관 대상 VM37대외부망 12 / 내부망 25 · vCenter·DNS 제외

설계 범위

구분설계 기준
대상 환경외부망·내부망 각각 vSphere 8(고객사 표기 VCF 8)과 별도 vCenter. 망마다 OpenShift 클러스터 1개와 MTV vSphere Provider 1개를 둡니다. DB 레거시 풀은 범위에서 제외합니다.
설치 방식전체 폐쇄망 UPI(platform: none). Master가 KVM VM이라 BMC가 없어 IPI를 쓰지 않습니다. 망별 Bastion이 미러 레지스트리·DNS·로드밸런서·NTP·Ignition HTTP를 제공하고, etcd 백업을 nasbak망으로 통합 백업스토리지에 보관합니다.
Control Plane망마다 KVM 호스트 1대에 Master VM 3식(외부: 재활용 TNS-2100, 내부: 기존 HV#03 재구성). Bootstrap은 같은 KVM 호스트의 임시 VM.
Compute기존 HV를 RHCOS Worker로 재구성. Worker1을 먼저 편입해 MTV 대상으로 쓰고, MTV 원본 HV는 안정화 후 Worker2로 전환합니다.
이관MTV 2.12. 방식은 ① Storage Copy Offload(1순위) / ② VDDK(라이선스 이슈, 사용 확정 시) / ③ Skip VDDK cold(대안). Preserve static IPs로 기존 IP를 유지합니다.

03. 네트워크 설계

실사 기준 (2026-10-12)
기존 HV는 vswitch 3개(서비스, nasbak, 관리·vMotion)에 각각 물리 포트 2개가 연결된 6포트 구성입니다. 관리망은 태그 없음, 서비스망 VLAN 130, nasbak망 VLAN 701·710이며 외부망·내부망이 같습니다. Worker로 전환하는 HV는 같은 물리 포트·HBA를 그대로 사용합니다.

한 망 기준 그림이며 외부망·내부망이 같은 구조입니다. 망별 장비 배정은 02장 망별 장비 재구성(행별 AS-IS → TO-BE)을 따릅니다. 각 Bastion은 관리 2포트와 etcd 백업용 NAS/BK 2포트(신규 포설)를 사용하며, OpenShift 노드와 달리 nasbak망에 호스트 IP를 둡니다. 노드 간 통신과 MTV 이관 트래픽(443·902)은 관리망 bond0을 사용하고, 서비스망·nasbak망은 노드 IP 없이 브리지로 VM에만 연결합니다. 기본 게이트웨이는 관리망에만 둡니다.

Worker는 기존 HV IP를 재사용하므로 신규 IP가 없습니다. API·Ingress는 Bastion LB를 쓰므로 별도 VIP가 필요 없고, Bootstrap IP는 설치 완료 후 반납할 수 있습니다. nasbak IP는 Bastion만 필요합니다(노드는 nasbak IP 없음).

IP 상세는 국데처 SGIS 구성 내부 문서를 기준으로 채웁니다. 호스트명 명명 규칙과 클러스터 이름·base domain은 09장 확정 항목입니다.

시간 동기화 (NTP) 설계

  • 구성: 망별 NTP 서버(망 내부) → Bastion(chronyd 클라이언트 겸 서버) → KVM 호스트·Master VM·Worker. 노드는 Bastion만 바라보므로 방화벽 규칙이 망당 1건으로 끝나고 Worker2 편입 시 추가 신청이 없습니다.
  • Bastion: /etc/chrony.conf에 망별 NTP 서버를 server로, 관리망 대역을 allow로 설정합니다.
  • RHCOS 노드: 설치 전 Master·Worker용 chrony MachineConfig(Bastion을 server로 지정)를 manifests에 넣어 설치 시점부터 동기화합니다. KVM 호스트는 chronyd를 직접 설정합니다.
  • 순서: 방화벽은 Bastion 구축(11월) 전에 개통되어야 합니다. 시간이 어긋나면 설치 중 인증서 검증·etcd 오류가 발생하므로 설치 전 Bastion·KVM 호스트의 동기화 상태(chronyc sources)를 확인합니다.

이관 기간에는 망마다 Worker1 한 대가 업무 VM 전체를 받습니다. 현재도 업무 VM은 망별 HV 1대(외부 HV#01·내부 HV#02)에 모여 있고, Worker1은 같은 사양이므로 아래 계산으로 수용 여부를 판단합니다.

망이관 VMvCPU 합계메모리 합계Worker1 CPU 요청Worker1 메모리 사용 예상판단

메모리 사용 예상 = VM 메모리 합계 + VM 관리 오버헤드(VM당 약 0.4GB) + 노드 예약(약 30GB) + 플랫폼 Pod(약 40GB)

  • CPU: OpenShift Virtualization은 기본적으로 vCPU를 10:1로 오버커밋하여 vCPU 1개당 0.1코어를 요청합니다. 현재 VMware에서도 내부망은 물리 48코어에 vCPU 196(약 4:1)으로 운영 중이므로 실사용률을 기준으로 판단합니다. 시험 이관 전 vCenter에서 호스트 CPU 사용률·CPU Ready를 확인합니다.
  • 메모리: 기본적으로 오버커밋하지 않으므로 VM 메모리 합계가 그대로 노드에 잡힙니다. Master가 스케줄 불가(06장)이므로 모니터링·Ingress·가상화·MTV·CSI 등 플랫폼 Pod도 Worker1에 올라갑니다. 노드 예약·플랫폼 Pod 값은 설계 가정이며 Worker1 편입 후 실측해 갱신합니다.
  • 이관 중 추가 부하: MTV 변환 Pod가 동시 이관 수만큼 Worker1에서 실행됩니다. 내부망은 마지막 회차의 여유가 가장 작으므로 시험 이관에서 변환 Pod 메모리를 측정해 마지막 회차의 동시 이관 수를 정합니다.
  • Worker2 편입 후: 망별 총 2TB가 되지만 노드 1대 장애 시 남은 1대가 망 전체 VM을 받아야 합니다. 내부망은 약 840GB로 1대에 수용되나 여유가 작으므로 내부망 VM 증설 시 재산정합니다.

VM 수·자원 합계는 2026-10-13 팀장 검토 기준이며 vCenter·DNS VM을 제외합니다. DNS VM은 망마다 1대(4코어 · 8GB, 로컬 디스크)로 MTV 대상이 아니며 Bastion DNS로 대체합니다. 스토리지 용량은 05장을 따릅니다.

스토리지 연결 준비

  • Worker 전환 HV: 같은 HBA를 사용하지만 OS를 재설치하므로 스토리지의 호스트 등록·마스킹 뷰를 스토리지 엔지니어와 재확인합니다. 재설치 전 VMFS LUN 매핑을 해제합니다(외부 HV#02·HV#01, 내부 HV#01·HV#02).
  • 내부 Master HV#03: 재구성 전에 VMFS LUN 매핑을 해제하고, Master KVM 호스트는 etcd·VM 디스크용 로컬 SSD/NVMe를 사용합니다.
  • 재활용 TNS-2100(외부 Master·외부/내부 Bastion): FC에 연결하지 않습니다. etcd는 Master KVM 호스트의 로컬 SSD/NVMe를 사용합니다(외부 TNS-2100·내부 HV#03).
  • RHCOS 멀티패스: Worker는 MachineConfig로 멀티패스를 적용하고 설치 디스크는 /dev/disk/by-id로 지정합니다.
  • Copy Offload 준비: 이관 대상 VM의 스냅샷을 삭제합니다(남아 있으면 소프트웨어 복사로 후퇴). ESXi SSH·VIB 허용과 스토리지 관리 계정은 VMware·스토리지 엔지니어와 정합니다.

동일 EMC 스토리지 사용 계획 — 이관 기간

스토리지 용량 산정

동일 EMC에서 기존 VMFS 데이터스토어를 유지하면서 MTV 대상 볼륨을 추가로 확보합니다. 원본 사용량은 74.7TB(외부 12.4 + 내부 62.3)이며 이관·원본 보관 기간에는 대상 볼륨이 동시에 필요하므로 약 74.7TB 이상의 추가 공간이 필요합니다. 기존 데이터스토어의 여유 공간은 거의 없으므로(외부 600GB 이상, 내부 200GB 이상) 스토리지 풀의 여유로 확보해야 합니다.

추가 필요 공간 = MTV 대상 볼륨(약 74.7TB) + 파일시스템·플랫폼 오버헤드 + 임시·스냅샷 공간 + 운영 여유
부족분 = max(0, 추가 필요 공간 − 사업에 할당 가능한 스토리지 잔여 용량)

사용량에 스냅샷·ISO 등이 포함되는지는 확인되지 않았습니다. 대상 PVC가 디스크 할당 크기만큼 잡히는지 실제 사용량만큼 잡히는지는 시험 이관에서 확인합니다. VMware 스냅샷은 데이터스토어를 더 채우므로 롤백 수단으로 쓰지 않습니다. 원본 삭제로 회수할 용량은 사전에 가용 공간으로 계산하지 않습니다.

Master KVM 호스트 구성

항목설계 값
OS · 가상화RHEL 9.8 + libvirt/KVM
네트워크bond0(관리 2포트, mode 1) 위 브리지 br0 · Master VM·Bootstrap은 br0에 연결 · NAS/BK 포설 없음(etcd 백업은 Bastion 경유)
VM 디스크로컬 SSD/NVMe · 가능하면 Master VM별 디스크 분리 · FC 연결 안 함
CPU · 메모리오버커밋 없음(04장 사양 합계 기준)
VM 자동 기동호스트 재부팅 시 Master VM 3식 자동 기동(libvirt autostart)

운영 제약

  • Worker1 단독 기간: Live Migration이 불가하므로 OCP 업데이트·MachineConfig 변경을 동결하고, 노드 재부팅이 필요한 작업은 VM 중단을 사전 공지합니다.
  • Master KVM 단일 호스트: KVM 호스트 재부팅 시 Master VM 3식이 함께 중단됩니다(운영 중인 VM은 Worker에서 계속 동작). 호스트 패치는 작업창을 잡고 진행합니다.
  • 원본 보관: 이관한 원본 VM은 VMware에 전원 종료 상태로 남습니다. 원본 HV를 Worker2로 전환하면 원본 VM은 사라지고, 원본 LUN 회수는 별도로 판단합니다.
